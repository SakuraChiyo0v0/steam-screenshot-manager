# 产品需求

状态：规划基线，2026-09-20。实现与验证均未开始。

## 1. 定位

为珍贵游戏截图建立独立于 Steam 社区上传服务的个人图库。电脑负责采集和浏览，用户自己的 WebDAV 负责存取。使用者不必懂 AppID、数据库或同步协议。

第一条完整用户路径是：发现截图 → 确认导入 → 本地浏览 → 绑定存储 → 上传并校验 → 新电脑选择性恢复。

## 2. 功能需求

| 编号 | 用户可见行为 | 首版判据 |
|---|---|---|
| FR-01 | 自动发现 Steam，也可手动指定路径、旧盘目录 | 支持多个根目录、多账号；不得仅选第一个账号 |
| FR-02 | 扫描预览按账号、游戏显示图片数、体积和异常 | 全部扫描选定范围；没有图片与扫描失败明确区分 |
| FR-03 | 采集常规截图、高质量副本、用户添加目录 | 保留 JPEG/PNG/AVIF/TGA 等识别格式；缩略图不当原件 |
| FR-04 | 将原件复制到用户选择的独立图库 | 不修改来源；写入失败不伪造已导入 |
| FR-05 | 按游戏浏览、搜索、排序、筛选截图 | 断网可用；支持大图、原文件名、时间来源、大小、版本与来源 |
| FR-06 | 查看本地和远端保存状态 | 已归档、待上传、上传中、待校验、远端已校验、恢复失败等状态明确 |
| FR-07 | 按规则导出到指定文件夹 | 支持游戏名、AppID、年份；冲突保留两份，不覆盖 |
| FR-08 | 绑定、测试和切换 WebDAV 连接 | 显示所选远端图库；失败给出可理解原因；切换不删除旧存储 |
| FR-09 | 上传全部或指定游戏 | 支持暂停、恢复、重试、进度、失败明细和基本限速 |
| FR-10 | 新电脑发现远端图库并下载指定游戏 | 不依赖旧数据库、旧电脑、Steam 登录或游戏已安装 |
| FR-11 | 自动收集新增截图 | 后台监听、启动补扫、休眠恢复补扫；自动上传需用户开启 |
| FR-12 | 需要时释放本机缓存 | 只有已确认远端完整的图库副本可清理；不清理 Steam 来源；远端保留 |

FR-12 放在首版最后阶段；在上传与恢复可靠性通过之前不提供清理按钮。

## 3. 页面与流程

### 初次设置

按顺序选择来源账号和目录、本地图库位置、可选 WebDAV。任何一步都可以暂缓配置远端，进入纯本地模式。预计额外空间不足时说明所需空间，不擅自移动或删除来源腾空间。图库目录不能等于来源目录，也不能与来源互相嵌套，以免重复扫描自身产物。

扫描完成后展示结果再导入；用户选择的范围持续有效，后续自动导入不反复弹窗。手动目录必须指定账号和游戏，或先进入待归类；未归类图片可本地保存，归类前不上传。

### 游戏列表

默认是“有截图的游戏”，可切换查看已安装游戏。在线拥有游戏集合是后续功能，不能拿已安装数量冒充完整库。列表展示游戏名、图片数、字节总量、最新拍摄时间、待上传与异常数量。没有封面时使用稳定占位，加载封面失败不阻断页面。

### 游戏详情

虚拟化网格，按时间或导入时间排序；可筛选账号、本地可用、仅远端、未校验、失败。时间不明时明确显示未知，不能把导入时间伪装成拍摄时间。原图不支持预览时，展示格式说明并允许导出/在外部程序打开。

首版相册只把字节一致的副本去重。相同画面的 JPG、PNG、HDR 版本分别保留；不承诺自动识别同一拍摄事件。

### 同步任务

区分扫描进度、复制字节数、传输字节数与校验进度。用户应看到哪个游戏、哪张图片失败、原因是什么、如何重试。暂停要停止调度新任务并安全处理中途任务；程序重启后仍能看见未完成任务。

### 设置

来源目录及账号选择、本地图库位置、WebDAV 连接与远端图库、自动收集/上传、托盘与开机启动、限速、导出规则、诊断信息。开机启动需用户开启。首版一个活动远端；切换时保留按远端区分的完成记录，不能把旧远端成功状态套给新远端。

## 4. 统计与状态定义

| 名称 | 定义 |
|---|---|
| 图片数 | 按账号＋游戏＋完整 SHA-256 去重后的原始文件数 |
| 来源数 | 文件从多少个路径/设备被发现，与图片数不同 |
| 原件总量 | 上述逻辑图片各计一次的字节数，不含预览与缓存 |
| 本机占用 | 当前设备图库实际占用，另列缓存；不把 Steam 原目录算进图库 |
| 远端已校验 | 当前远端上的原件已读回校验，且对应完整记录已确认发布 |
| 本机可用 | 受管理的本地原件当前存在且经过导入/下载完整性验证；缺失后撤销状态 |
| 远端已收录 | 已读到有效远端记录，未必在本设备重新读取并校验原件 |

远端可能存在重复物理对象，不能把逻辑原件总量标成“服务端实际占用”。清单声称有图不等于原件现在仍存在；下载失败后显示远端异常，不继续显示可恢复保证。

## 5. 数据保护行为

- 来源被删：保留独立图库和远端，标记来源不可用。
- 游戏卸载：仍显示其截图。
- 远端文件丢失：提示异常，有本地完整原件时可补传。
- 远端不可达：继续本地采集，任务等待重试；不将空响应解释成空图库。
- 清理本机：重新确认目标远端原件可读且哈希一致后才删除应用管理的副本；绝不触碰来源。
- 首版无远端删除、标签跨端编辑、图库合并或垃圾回收。游戏别名、收藏等如有实现，先明确是本机设置；不伪装成已同步。

## 6. 非功能目标

目标平台 Windows x64；无网络仍可采集浏览；百万字节级以上文件使用流处理，避免全量装入内存。哈希、扫描与缩略图任务不阻塞窗口。数据库与文件任务均能从崩溃中恢复。

建议以 10,000 张混合图片验收分页与任务恢复，以 100,000 条索引做扩展性检查。具体耗时和内存必须在固定硬件上报告实测；不预先宣称未经测量的性能数字。

## 7. 后续增强

可选 Steam 账号登录与完整拥有游戏库、Linux/Steam Deck、macOS、只读 NAS 图库网页、更多存储后端、跨端标签编辑、带恢复窗口的明确删除。每项独立规划，不为未来可能性提前实现通用插件平台。

2026-09-20 在真实数据上实测发现两类首版范围外的数据，各自独立规划，不因它们存在而扩大首版：

- **Steam 自带录屏与剪辑（Game Recording）**：实测 44.6 GB / 13,944 个文件，含导出片段与后台录制，内部为 MPEG-DASH + HEVC 分片。与截图目录完全独立。详见[真实数据快照](evidence/real-data-structure.md)。
- **截图与录屏时间轴的关联**：时间轴 JSON 把截图事件和成就事件按录制时间点记在同一条时间线上（实测 418 个截图事件），截图索引侧以 `timelineid`/`timelinetime` 回指。若做"按时间轴看截图"可直接复用这条关联链。
